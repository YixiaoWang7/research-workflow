# Project Execution Rules

These rules apply to every machine and project that runs long training, data collection,
or evaluation jobs. Project-specific values belong in versioned configuration, not in
memory, chat history, or undocumented shell variables.

## 1. New project initialization

When the user gives Codex only this file for a new or existing project, Codex must:

1. Read this file completely, identify the repository root, and inspect the project language,
   structure, commands, tests, generated artifacts, training/evaluation entrypoints, and Git
   conventions before editing.
2. Check for an existing project `AGENTS.md`. If absent, create a concise project-specific guide.
   If present, preserve its repository-specific instructions and add only missing requirements;
   never replace it blindly.
3. Create or adapt `docs/README.md`, `docs/operations.md`, and `WORKING.md`. If the project runs
   training or evaluation, also create `docs/experiments/README.md`. For any multi-stage training,
   collection, evaluation, or deployment pipeline, maintain a clearly named task guide or
   verified-command runbook under `docs/` using the standards below. Replace all placeholders
   with real project paths, commands, objectives, stages, dependencies, and completion gates.
   Link every active document from `docs/README.md`, and link that map from the root `README.md`.
4. If the project contains training or evaluation, configure supported workflows for online W&B
   using entity `yixiao_wang` and an explicit project-specific project name. Add fail-fast checks,
   tests, and documentation. If no such workflows exist, do not invent them.
5. Add generated runs, datasets, checkpoints, logs, videos, and W&B caches to `.gitignore` without
   hiding source, configuration, fixtures, or required documentation.
6. Run the project's relevant tests, formatter/linter, and documentation/link checks. Record the
   results and any genuine pre-existing failures in `WORKING.md`; do not claim compliance without
   evidence.
7. Report what was created or changed and the first unfinished action. Do not launch expensive
   training, publish externally, delete data, commit, or push unless the user has authorized it.

This initialization procedure makes `rules.md` self-contained. A parent `AGENTS.md` can automate
loading it, but is optional when the user explicitly asks Codex to read this file.

### New-machine deployment

When bringing an existing repository to another machine, Codex must read the project's verified
pipeline-command runbook and the latest relevant record under `docs/experiments/` before launching
work. Recreate and smoke-test the documented software environment, check required assets and
storage, verify W&B authentication and destination, and record the new machine in `WORKING.md`.
Treat parallel-environment counts, batch sizes, worker counts, and throughput estimates as
hardware-specific: begin with a bounded smoke test, benchmark resource-sensitive settings on the
new machine, and update the recommendation only after the result passes output validation. Never
copy a previous machine's maximum setting blindly.

## 2. Cloud experiment tracking

- Enable W&B by default for every training and evaluation workflow.
- Use W&B entity `yixiao_wang`. Each project must define a stable project name in its
  checked-in configuration; do not rely on W&B's implicit/default entity.
- Default to online mode. Offline mode or TensorBoard-only logging requires an explicit
  user request.
- Before a long job, run `wandb login --verify`. Store credentials through W&B (normally
  `~/.netrc`); never place API keys in source, configuration, documentation, logs, or chat.
- Training runs must upload metrics, resolved configuration, provenance, and checkpoints.
  Evaluations must create separate W&B runs with aggregate metrics and result artifacts.
- Confirm that startup prints a valid URL of the form
  `https://wandb.ai/yixiao_wang/<project>/runs/<run-id>`. Treat missing, malformed, or 404
  URLs as failures and fix them immediately. Never claim an upload succeeded based only
  on a local `wandb sync` exit code; verify the run with the W&B API or website.

## 3. Durable background execution

- Long jobs must run independently of an editor, SSH connection, chat turn, or tool PTY.
  Use the machine's scheduler when available; otherwise use `systemd-run`, `tmux`, or
  `setsid` plus `nohup`, with stdout/stderr redirected to a known log file.
- Record the actual worker PID and OS session/process-group ID or scheduler job ID. An
  assistant tool's temporary session ID is not a durable job identifier.
- Immediately verify four signals: worker process exists, output advances, accelerator or
  CPU memory is allocated, and the cloud run is visible.
- In managed or sandboxed environments, a normal `ps` command may run in a different process
  namespace and hide detached host jobs. A missing sandbox-visible PID is not evidence that a
  job stopped. Before declaring failure, use an authorized host-level process check and confirm
  at least one independent signal such as advancing logs, accelerator process listings, new
  checkpoints, or the W&B heartbeat.
- Monitor healthy long jobs with a detached local watcher so routine checks do not consume
  assistant turns or model tokens. Prefer an event-driven supervisor that launches the worker
  and waits for its exit directly. When supervising an existing PID, use ETA-aware local polling:
  check every 15–30 minutes while completion is hours away, every 5–10 minutes in the final hour,
  and every 1–2 minutes only in the final ten minutes or during failure diagnosis. These local
  checks are token-free; emit conversation-visible updates only for state transitions, meaningful
  milestones, failures, or completion. Never stop monitoring merely to avoid token use.
- A one-shot stage supervisor is not a complete monitor. Keep a separate durable pipeline
  watchdog alive across stage exits. It must notice success or failure promptly, start the next
  eligible stage, retry clearly transient infrastructure failures a bounded number of times, and
  remain in a recorded `needs_attention` state after an unrecoverable failure instead of silently
  disappearing. Use an external notification mechanism when the project already provides one.
- Before leaving a long chain unattended, test the exact detached invocation and environment,
  not only argument parsing. Use absolute interpreter and script paths; set required variables
  such as `TERM`, `PATH`, credentials mode, device, and cache directories explicitly. Do not call
  an environment-dependent wrapper from a detached process unless the environment is activated
  inside that same command. For IsaacLab, prefer the known environment's absolute Python path.
- Write supervisor state atomically and include a run/generation identifier. Downstream watchers
  must distinguish stale failure records from a newly started upstream generation. Validate the
  first real subprocess startup before declaring the chain safely queued.
- Do not launch a dependent stage until its input artifact exists and its quality gate
  passes. Record queued stages explicitly.

## 4. Standard project documents

Every project should keep this structure:

- `README.md`: purpose, installation, and quick start.
- `AGENTS.md`: repository boundaries, commands, style, tests, and operational rules.
- `docs/README.md`: short documentation map stating the purpose of every active document and the
  reading path for each task. Link it from the root README.
- `docs/<task-or-pipeline>.md`: stable, reusable configuration, commands, contracts, quality gates,
  and expected outputs. Prefer one guide per task or pipeline.
- `docs/operations.md`: stable runbook for launching, verifying, recovering, and stopping
  background jobs and for W&B setup.
- `WORKING.md`: live machine-local execution ledger. Update it whenever a job starts,
  stops, fails, completes, or changes the queue. Do not place credentials in it.
- `docs/experiments/README.md`: index and naming policy for permanent experiment records.
- `docs/experiments/<task>-<YYYY-MM-DD>-<label>.md`: concise, immutable evidence for each completed
  production or reference run, following section 7.
- Additional reference documents only when their content would make the task guide unwieldy.

Generated data, logs, videos, checkpoints, and W&B caches should remain gitignored. The
documents should identify their locations instead of copying generated content into Git. Use
lowercase kebab-case filenames under `docs/`. Avoid redundant pointer pages, stale task lists, and
one-off result files at the top level of `docs/`; consolidate them or place dated records under
`docs/experiments/`.

## 5. Session startup and handoff protocol

- At the beginning of every session, locate the repository root and read `AGENTS.md`,
  `WORKING.md`, the relevant verified pipeline-command runbook, and the relevant operational or
  workflow documentation before running commands. Read the latest relevant experiment record when
  reproducing, comparing, or extending a completed run.
- `AGENTS.md` describes how to work; its existence or maintenance is not the project's active
  objective. The current objective and remaining stages come from `WORKING.md`.
- Treat `WORKING.md` as the source of truth for unfinished work; never depend on chat history.
  If it is missing, create it from the template below before starting a long pipeline.
- Reconcile the ledger with reality: verify listed PIDs or scheduler IDs, inspect the latest
  log/checkpoint, and confirm W&B state. Mark stale jobs failed or interrupted rather than
  assuming that a `running` row is still correct.
- Continue the first eligible queued stage whose inputs and quality gate are satisfied. Do not
  rerun completed stages unless their recorded evidence is missing or invalid.
- Unless the user explicitly asks for a status-only inspection or says not to resume, treat a
  session with non-complete `WORKING.md` rows as authorization to continue the recorded objective.
  Do not stop after summarizing status or confirming that a background process is alive.
- "Continue the work" means taking operational ownership through the recorded completion gates:
  verify and take over monitoring of live jobs, keep a durable local watchdog running, follow
  stage transitions, diagnose stalls and failures, apply safe in-scope fixes or bounded retries,
  and start each newly eligible downstream stage. Ask the user only when recovery requires a
  destructive action, new external authority, or a material choice not settled by the ledger.
- When durable goals are available, create or continue one covering every non-complete pipeline
  row. Use detached local watchers for frequent polling so healthy waits consume no model tokens;
  spend assistant turns on meaningful milestones, ETA boundaries, anomalous or stale state, and
  required intervention. A watchdog entering `needs_attention` is a trigger for Codex to
  investigate and resolve the problem, not a final handoff state.
- Never implement monitoring as frequent model-driven polling. For a healthy run expected to take
  hours (for example, ten hours), do not wake Codex every minute or reread full logs on every
  check. Let a detached local watcher poll at the ETA-aware cadence in section 3 and write a small
  atomic state file. Schedule Codex reasoning near meaningful milestones or the projected finish,
  and immediately when the watcher reports an error, stale heartbeat, exited worker, or completed
  stage. On each Codex check, read the compact state and process handle first; open only the
  relevant log tail or artifact when those signals require deeper diagnosis.
- When asked what remains, report every pipeline row whose status is not `complete`, including
  its blockers and next eligible action. Do not answer only that an instruction file exists.
- Treat statements such as "end session", "stop here", "prepare handoff", "close the
  conversation", or equivalent intent as an explicit handoff trigger. Before replying, verify
  active jobs from the host plus at least one independent signal, then update the pipeline table,
  active jobs, completed/failed jobs, remaining non-complete stages, blockers, ETA, last
  verification, and one explicit next action in `WORKING.md`.
- During that handoff, also inspect the verified pipeline-command runbook. Update it if this
  session produced validated changes to commands or recommendations; otherwise leave it stable.
  If a production or reference experiment completed, create or finish its dated record under
  `docs/experiments/`, add it to the experiment index, and link it from the task guide before
  allowing `WORKING.md` to move to another objective. The ledger, runbook, and experiment records
  together must be sufficient for a new Codex session with the repository and this `rules.md`, but
  no access to previous conversation history.
- Codex cannot detect that a user closed a client without sending a message. Perform the full
  handoff whenever ending intent is expressed, and maintain `WORKING.md` at material state
  transitions so an unexpected disconnect still loses as little context as possible.

## 6. Verified pipeline-command runbook

For each multi-stage production pipeline, maintain one discoverable runbook such as
`docs/catching-y.md` or `docs/catching-y-commands.md`. Choose a descriptive lowercase kebab-case
name based on the actual pipeline; do not mechanically use the example name in unrelated projects.
The runbook must:

1. State the required order of stages and the artifact or quality gate passed between them.
2. Include environment/bootstrap commands, dependency and asset checks, and a cheap smoke test.
3. Record copyable known-good commands for training, checkpoint selection, held-out evaluation,
   data collection, validation, merge/preparation, deployment, and other applicable stages.
4. Pin all correctness-critical values: config path, task, seed policy, device, parallelism,
   training budget, checkpoint/descriptor handoff, data size, sampling, encoding, output layout,
   and validation gates. Explain which values must be unique for each run or shard.
5. For W&B workflows, explicitly record online mode, entity `yixiao_wang`, project name, logger
   flags, login verification, and the required run-URL pattern. Distinguish local output paths
   from W&B runs and never record credentials.
6. Keep reusable recommendations separate from historical exact invocations. Put run IDs, dated
   output directories, selected checkpoint hashes, results, and W&B links in a dated experiment
   record, then link that record from the runbook.
7. Identify machine-specific recommendations and cite their validation evidence: machine/GPU,
   test date, tested range, throughput, peak RAM/VRAM, and why the recommended point was selected.
8. Include post-stage validation commands and concrete completion criteria. A process exit alone
   is not a validated result.

Update this runbook only after tests, a benchmark, or a successful production run validates a
procedure change. Update it when commands, environment variables, W&B routing, stage order,
quality gates, data contracts, checkpoint rules, parallelism, sharding, or validation steps
change. Do not put PIDs, current progress, transient ETAs, or routine status in it; those belong
in `WORKING.md`. Link the runbook from `README.md`, `docs/operations.md`, or the canonical workflow
guide so a new agent can discover it without chat history.

## 7. Versioned experiment records

For every completed production run or reference benchmark, create a small tracked file at
`docs/experiments/<task>-<YYYY-MM-DD>-<label>.md`. This is required because `WORKING.md` is reused
for future tasks and generated `runs/`, `data/`, and `outputs/` directories may never be committed.
The record must remain useful in a fresh clone even when local artifacts are absent.

Each record must include:

1. Completion status and timestamp, task ID, objective, machine/GPU, software environment, and any
   material limitation.
2. Version identity: Git commit or branch when available, configuration paths and hashes, seeds,
   training budget, evaluation protocol, and important hardware-dependent settings.
3. Concise, copyable commands or command templates for every completed stage. Use repository-
   relative paths where possible and never include credentials.
4. Dataset identity, size, schema/sampling details, validation result, and local or remote location.
5. Selected checkpoint and descriptor paths plus SHA-256 hashes where available.
6. Headline metrics with definitions and evaluation sample counts. Include per-category metrics
   only when they are necessary to interpret the result.
7. Direct W&B URLs for each training and evaluation run, clearly labeled by stage.
8. Validation evidence, failed or superseded attempts that materially affect interpretation, and
   the location of any more detailed local report.

Keep the record concise; summarize logs rather than copying them. Treat a published record as an
immutable snapshot: correct factual mistakes explicitly, but never overwrite it with a later run.
Create a new dated record for the later run, add both to `docs/experiments/README.md`, and keep the
relevant task guide linked to the useful baselines. A path under an ignored directory may be
recorded for provenance, but it must not be the only place containing the commands, metrics,
checkpoint identities, or W&B URLs.

Minimal template:

```markdown
# <Task> <Label> — YYYY-MM-DD

## Summary
<status, objective, task/config identity, machine, budgets, and seeds>

## Commands
<essential reproducible commands>

## Results and W&B
<metric table with sample counts and labeled training/evaluation URLs>

## Persistent artifact identities
<dataset/checkpoint/descriptor paths, hashes, and validation evidence>
```

## 9. Completion checklist

Before declaring a pipeline complete, verify: tests and lint pass; every requested stage
finished; metrics and artifacts are present locally and in W&B; evaluation uses held-out
seeds; failures and abandoned outputs are labeled; and `WORKING.md` reflects the final
state. For a production or reference result, also verify that a dated experiment record exists,
is indexed, is linked from the task guide, and contains enough evidence to survive deletion of
ignored outputs. Report exact paths, cloud URLs, parameters, and scores.
